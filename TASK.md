# ТЗ: веб-приложение для чтения и скачивания ранобэ на базе `ranobelib-python-sdk`

## Контекст

`ranobelib-python-sdk` (этот репозиторий) — асинхронный Python SDK для сайта ranobelib.me:
получение метаданных тайтла, чтение оглавления, скачивание отдельных глав/томов/тайтла
целиком и экспорт в epub/fb2/txt/pdf. SDK уже стабилен (v0.3.0), покрыт тестами (95%+) и
публикуется на PyPI как `ranobelib-python-sdk` (импортируется как `ranobelib`).

Задача — спроектировать и реализовать веб-приложение, которое даёт то же самое через
браузер: вставил ссылку на тайтл → посмотрел информацию/оглавление → почитал главу онлайн
или скачал файл в нужном формате. **Веб-приложение — это тонкий слой поверх SDK**: вся
логика похода в API ranobelib, ретраи, кэш сырых ответов, парсинг контента и генерация
epub/fb2/txt/pdf уже реализованы в SDK и не должны дублироваться на уровне сайта.

Это отдельный проект (новый репозиторий), использующий `ranobelib-python-sdk` как
зависимость. Ниже — то, что должно быть реализовано, а не то, как именно; выбор конкретного
веб-фреймворка и деталей UI/UX оставлен на усмотрение реализующего, с рекомендациями там,
где это уместно.

## 1. Функциональность SDK (то, что должен покрыть сайт)

Публичный контракт SDK — класс `RanobeLib`, инициализируется ссылкой на тайтл или его
`{id}--{slug}`-идентификатором:

| Метод SDK | Что делает | Что должно дать веб-приложение |
|---|---|---|
| `get_info()` | Метаданные тайтла: названия (ориг./рус./англ./другие), обложка (4 размера), описание, дата релиза, статус, возрастное ограничение, лицензирован ли, жанры, теги, авторы, художники, переводческие команды, число глав | Страница тайтла с этими данными |
| `get_table_of_contents()` | Список томов и глав (номер, название, номер главы вида `"51.6"` для дробных, число доступных переводов) без контента | Оглавление тайтла — список томов, раскрывающийся список глав |
| `get_chapter(volume, number, branch_id=...)` | Контент одной главы (HTML: параграфы, `strong`/`em`, `<br>`, картинки) | Онлайн-чтение главы; скачивание одной главы |
| `get_chapters([(volume, number), ...])` | Несколько произвольных глав разом | Массовое скачивание/экспорт выбранных глав |
| `get_volume(volume)` / `get_volumes([...])` | Весь том / несколько томов целиком | Скачивание тома целиком |
| `get_translations(volume, number)` | Список переводов (команд/загрузивших) для главы, у которой их несколько | UI выбора перевода, когда у главы `branches_count > 1` |
| `download_title(branch_id=..., translation_index=..., chapter_delay=...)` | Весь тайтл целиком, одним вызовом, с постраничной паузой | «Скачать весь тайтл» — с прогрессом, т.к. может занимать долго |
| `export(chapters, fmt=..., path=...)` | Экспорт списка глав в `txt`/`fb2`/`epub`/`pdf` (обложка + иллюстрации встраиваются в epub/pdf) | Кнопка «Экспортировать» с выбором формата, отдающая файл на скачивание |

Доступные форматы экспорта не хардкодить — брать из `ranobelib.exporters.EXPORTERS`
(словарь `{имя_формата: класс}`), т.к. `pdf` регистрируется только если на сервере доступен
WeasyPrint (нативные библиотеки Pango/cairo/GTK3, см. `docs/api-notes.md` этого репозитория,
раздел «PDF export») — если их нет, `EXPORTERS` просто не будет содержать `"pdf"`, и сайт
должен молча не показывать эту опцию, а не падать.

### Исключения SDK → как показывать пользователю

Все исключения — подклассы `ranobelib.RanobeLibError`. Сайт должен ловить их на границе
(API-слое) и превращать в понятные ответы/сообщения, а не отдавать пользователю трейсбек:

| Исключение | Когда | Что показать пользователю |
|---|---|---|
| `TitleNotFoundError` | Тайтл не найден по ссылке | «Тайтл не найден, проверьте ссылку» (404) |
| `ChapterNotFoundError` | Нет главы с таким томом/номером | «Глава не найдена» (404) |
| `VolumeNotFoundError` | Нет глав в этом томе | «Том не найден» (404) |
| `MultipleTranslationsError` | У главы >1 перевода, `branch_id` не передан | Показать список вариантов (`.branches`, у каждого — команда/переводчик) и дать выбрать |
| `MultipleTitleTranslationsError` | То же самое, но при `download_title()` — сразу для всех неоднозначных глав тайтла | Показать список всех неоднозначных глав с их вариантами; либо дать выбрать по каждой, либо предложить общий `branch_id`/`translation_index` на весь тайтл |
| `AuthRequiredError` | Платный/ранний доступ (403) | «Требуется авторизация — недоступно» (SDK её не поддерживает, см. ниже) |
| `RateLimitError` | 429 после исчерпания ретраев самого SDK | «Сервис ranobelib сейчас ограничивает запросы, попробуйте позже» |

## 2. Функции веб-приложения

### 2.1. Поиск/открытие тайтла
- Поле ввода ссылки на тайтл (`https://ranobelib.me/ru/book/...`) или его
  `{id}--{slug}`-идентификатора — на вход `RanobeLib(url)` годится и то, и другое
  (см. `numbering.parse_slug_url`).
- Валидация ссылки на клиенте — best-effort, финальная проверка — реальный ответ API
  (`TitleNotFoundError`).
- Список недавно открытых тайтлов (история) — приятная опция, не критична для MVP.

### 2.2. Страница тайтла
- Обложка (взять лучшее доступное из `Cover`: `default` → `md` → `thumbnail`), название
  (ориг./рус./англ., другие названия), статус, возрастное ограничение, лицензирован ли,
  дата релиза, число глав, описание, жанры, теги, авторы, художники, переводческие команды.
- Оглавление: тома → главы (номер, название), с корректной сортировкой дробных номеров
  (используется та же логика, что в `numbering.py` — не переизобретать сортировку на
  фронтенде, том/номер уже приходят в нужном порядке из `get_table_of_contents()`).
- У главы с несколькими переводами — индикатор (например бейдж «N переводов»).

### 2.3. Чтение онлайн
- Открыть главу → рендер её HTML-контента (`Chapter.content`) как есть — это уже
  санитизированный SDK-ом HTML с ограниченным набором тегов (`p`, `strong`, `em`, `br`,
  `hr`, `img`), безопасный для вставки, но задача сайта — не доверять этому вслепую на
  границе с браузером: экранировать/санитизировать на выходе так же, как для любого чужого
  HTML, если он проходит через шаблонизатор без auto-escape, либо явно задокументировать,
  что рендер полагается на гарантии SDK.
- Навигация «предыдущая/следующая глава» в пределах тайтла.
- Если у главы несколько переводов и `branch_id` не выбран — сайт обязан сначала показать
  выбор (см. `MultipleTranslationsError` выше), не имеет права угадывать сам — тот же
  принцип, что и в самом SDK (см. `CLAUDE.md` этого репозитория, раздел «Публичный API»,
  пункт 7: собственный дефолт API непредсказуем).

### 2.4. Скачивание и экспорт
- Скачать одну главу в выбранном формате.
- Выбрать несколько глав (чекбоксы в оглавлении) → экспортировать разом одним файлом.
- Скачать том целиком / несколько томов.
- Скачать тайтл целиком (`download_title()`).
- Выбор формата — `txt`/`fb2`/`epub`/`pdf` (динамически из `EXPORTERS`, см. выше).
- Отдать пользователю итоговый файл (Content-Disposition: attachment), не оставлять мусор
  на сервере — временный файл экспорта должен быть удалён после отдачи ответа (или отдан
  из памяти/потока, если формат это позволяет).

### 2.5. Долгие операции (важно — архитектурное решение)
`download_title()` и экспорт большого числа глав могут занимать заметное время (десятки–
сотни последовательных запросов к API, плюс собственный пейсинг `ApiClient`, плюс
опциональный `chapter_delay`). Синхронный HTTP-запрос «нажал скачать → жду ответ» может
упереться в таймауты (браузера, прокси, самого сервера). Нужно явно выбрать один из
подходов и не мешать их наугад:
- **Фоновая задача + прогресс**: старт скачивания создаёт job (in-memory очередь для
  однопроцессного деплоя, либо Redis/RQ/Celery для более серьёзного), сайт опрашивает
  статус (polling) или получает обновления через SSE/WebSocket, по завершении — ссылка на
  скачивание готового файла.
- **Потоковая отдача**: для отдельной главы/тома это, вероятно, не нужно — время отклика
  и так приемлемое; для полного тайтла — обосновать выбор в реализации, если решат не
  делать background job, а стримить синхронно.

Не должно быть варианта «просто ждать 5 минут без обратной связи, пока браузерный запрос
висит» — как минимум индикатор прогресса (например «глава N из M») обязателен для
`download_title()`.

### 2.6. Обработка ошибок
- Единый маппинг исключений SDK → HTTP-статусы/сообщения (см. таблицу в разделе 1) на
  уровне API-слоя сайта, не размазанный по каждому обработчику отдельно.
- Понятные, не техничные сообщения пользователю; технические детали (если нужны) — в логах
  сервера, не в ответе.

### 2.7. Кэширование
- `RanobeLib(..., cache_dir=..., cache_ttl=...)` уже кэширует сырые ответы API на диск
  (метаданные тайтла, список глав, контент главы — отдельные неймспейсы). Сайт не должен
  заводить свой отдельный кэш этих же данных поверх — переиспользовать SDK-кэш, выбрав
  осознанно:
  - Один общий `cache_dir` на весь сайт (кэш переиспользуется между всеми пользователями,
    т.к. это публичные данные одного и того же внешнего API) — вероятно, правильный выбор
    по умолчанию, а не кэш на пользователя/сессию.
  - `cache_ttl` — решить, насколько «свежими» должны быть оглавление/список глав (важно
    для «допишите проду свежую главу — увидят ли её сразу без ручного `refresh=True`»).
  - Где физически лежит `cache_dir` при деплое (персистентный volume, если контейнер) —
    иначе кэш бесполезен между рестартами (не критично, но стоит явно решить, а не
    получить это как побочный эффект).

### 2.8. Ограничения, унаследованные от SDK (не пытаться обойти на уровне сайта)
- Только открытый контент — SDK не реализует авторизацию (см. `CLAUDE.md`,
  «Ключевые технические решения»), платные/ранние главы дают `AuthRequiredError`. Сайт не
  должен предлагать пользователю логин/пароль от ranobelib — такой функциональности нет
  и не планируется на уровне SDK.
- Rate limiting и конкурентность к `api.cdnlibs.org` уже управляются `ApiClient`
  (семафор, пейсинг, backoff) — сайт не должен добавлять свой параллельный слой запросов
  к тому же API в обход `RanobeLib`/`ApiClient` (например, дергать несколько
  `RanobeLib`-инстансов на один и тот же тайтл параллельно ради ускорения) — это сведёт на
  нет уже продуманный рейт-лимитинг.

## 3. Технические рекомендации (не жёсткий протокол)

- **Backend**: async-фреймворк, естественно сочетающийся с `httpx`/pydantic v2-стеком SDK
  (например FastAPI) — избегать sync-фреймворка, который заставил бы оборачивать все вызовы
  SDK в `asyncio.run()`/thread-пулы на каждый запрос.
- **Пакетный менеджер**: `uv`, как и в SDK-репозитории, если нет причины поступить иначе.
- **Зависимость на SDK**: пакет уже опубликован на PyPI как `ranobelib-python-sdk`
  (текущая версия — `0.3.0`, проверено на `pypi.org`), сайт подключает его обычной
  зависимостью (`uv add ranobelib-python-sdk`), без path/git-зависимости на этот
  репозиторий. Закрепить нижнюю границу версии (`ranobelib-python-sdk>=0.3.0`), т.к. ТЗ
  опирается на публичный контракт, зафиксированный в этой версии (`download_title`,
  `MultipleTitleTranslationsError`, exporters-реестр и т.д.) — если SDK в будущем выпустит
  breaking change, сверяться с его `CHANGELOG.md`.
- **Frontend**: на усмотрение реализующего — сайт достаточно простой (несколько страниц:
  поиск, тайтл, чтение, статус экспорта), тяжёлый SPA-фреймворк не обязателен, но не
  исключается, если удобнее для прогресс-бара долгих операций (2.5).
- Каждая фича из раздела 2 — по аналогии с git workflow исходного SDK-репозитория
  (`CLAUDE.md`, «Git workflow») имеет смысл вести отдельными атомарными коммитами/PR, а не
  одним гигантским коммитом — решение за тем, кто ведёт разработку сайта.

## 4. Не входит в объём (явно не делать)

- Авторизация на ranobelib.me / платный контент — SDK этого не умеет (см. 2.8).
- Изменение/загрузка контента на ranobelib.me — SDK и API только на чтение.
- Полнотекстовый поиск по всем тайтлам сети lib.social — SDK работает с одним тайтлом по
  ссылке, поиск по каталогу не реализован ни в SDK, ни в этом ТЗ.
- Иллюстрации в fb2/txt-экспорте — сознательное ограничение самого SDK (см. `CLAUDE.md`,
  таблица «Ключевые технические решения», строка «Иллюстрации»), сайт не должен создавать
  впечатление, что это возможно для этих двух форматов.
