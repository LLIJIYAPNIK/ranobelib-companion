# CLAUDE.md

Это новый репозиторий веб-приложения для чтения и скачивания ранобэ поверх
`ranobelib-python-sdk`. Полное ТЗ — в `TASK.md` в корне репозитория (перенеси туда
исходный документ, если его там ещё нет). Этот файл — оперативные инструкции для работы
в кодовой базе; при противоречии с ТЗ приоритет у ТЗ, а несоответствия — повод остановиться
и спросить, а не додумать самому.

## Что это за проект

Тонкий веб-слой поверх стабильного SDK (`ranobelib` на PyPI, `ranobelib-python-sdk>=0.3.0`).
Вся логика похода в API ranobelib.me, ретраи, рейт-лимитинг, кэш сырых ответов, парсинг
контента и генерация epub/fb2/txt/pdf — уже в SDK. Задача этого репозитория — UI и HTTP-слой
вокруг него, ничего из вышеперечисленного не дублировать и не переизобретать.

Golden rule: если чувствуешь, что пишешь код, который обходит SDK, добавляет параллельный
кэш тех же данных или сам сортирует/парсит номера глав — остановись, это, скорее всего,
уже сделано в SDK и его нужно просто вызвать.

### SDK — живая зависимость, не заморозка на 0.3.0

`ranobelib-python-sdk` активно разрабатывается, в нём могут появляться новые методы/поля/
возможности после `0.3.0`. Из этого следуют два обязательных правила, оба — до, а не после
того, как начал писать код:

1. **Перед тем как реализовывать что-либо своими руками на уровне сайта** (парсинг, доп.
   поле метаданных, недостающий фильтр, любую логику, которая выглядит как «логика про
   ранобэ», а не «логика веб-слоя») — сначала проверить PyPI, нет ли уже нужного в более
   свежей версии SDK, чем та, что закреплена в `pyproject.toml` (`pip index versions
   ranobelib-python-sdk`, страница пакета на pypi.org, `CHANGELOG.md` SDK). Не изобретать
   решение самостоятельно, не проверив это в первую очередь.
2. **Если нужной возможности нет даже в последней версии SDK** — завести issue в репозитории
   SDK: https://github.com/LLIJIYAPNIK/ranobelib-python-sdk/issues — что нужно и зачем,
   желательно с предлагаемой сигнатурой метода/примером использования, как остальной
   публичный API SDK. Не молча реализовывать эту логику внутри сайта в обход SDK. Сначала
   issue, потом — при необходимости — временный воркэраунд на сайте, явно помеченный как
   временный до появления фичи в SDK (например TODO-комментарием со ссылкой на issue).

Это тот же Golden rule, только сдвинутый по времени: не только «не дублируй то, что уже
есть в SDK», но и «не дублируй то, что скоро может появиться в SDK, вместо того чтобы это
туда предложить». Вся предметная логика про ранобэ (парсинг контента, номера глав,
экспорт, работа с API ranobelib.me) должна жить в SDK — этот репозиторий как был, так и
остаётся тонкой обёрткой вокруг него, а не местом, куда постепенно перетекает бизнес-логика.

## Стек и инструменты

- **Backend**: FastAPI (async, естественно сочетается с httpx/pydantic v2 стеком SDK).
  Не оборачивать вызовы SDK в `asyncio.run()` или thread-пулы — весь путь запроса должен
  быть async.
- **Пакетный менеджер**: `uv`. Зависимости — `uv add`, запуск — `uv run`.
- **Зависимость на SDK**: обычная PyPI-зависимость, `ranobelib-python-sdk>=0.3.0`. Никогда
  не переключать на path/git-зависимость на локальную копию SDK-репозитория, даже временно
  для отладки — если кажется, что в SDK баг, завести это отдельно, а не патчить его исходники
  внутри этого репозитория.
- **Фоновые задачи**: для MVP — in-memory job-очередь (однопроцессный деплой). Если понадобится
  горизонтальное масштабирование — Redis/RQ/Celery, но не вводить эту зависимость заранее
  без явной необходимости.
- **Frontend**: сервер-рендеринг (Jinja2) + минимум JS для интерактивности (выбор глав
  чекбоксами, поллинг/SSE прогресса долгих операций). Тяжёлый SPA-фреймворк не нужен, если
  не появится веская причина. Визуальная реализация экранов — не изобретать вёрстку заново,
  импортировать из Claude Design (см. раздел «Дизайн» ниже); `DESIGN_PROMPT.md` в корне
  репозитория — исходный промпт, из которого получены три концепции, оставлен для истории/
  контекста, актуальный источник вёрстки — сам файл концепции в Claude Design.
- **Данные приложения (пользователи, личная библиотека, активность, история загрузок)**:
  отдельная БД приложения (SQLite для MVP, `app/db/`) — не путать с SDK `cache_dir`, который
  остаётся публичным общим кэшем сырых ответов ranobelib.me. Хэш паролей — passlib/bcrypt,
  серверные сессии — стандартный session cookie (например `itsdangerous`/Starlette
  `SessionMiddleware`), без сторонних OAuth-провайдеров и без какой-либо интеграции с
  аккаунтом на ranobelib.me.

## Архитектура

```
app/
  api/            # HTTP-роуты (тонкие, без бизнес-логики)
  services/        # обёртка над RanobeLib: единственное место, где вызывается SDK
  auth/             # регистрация/логин/логаут, хэш паролей, сессии — уровень приложения,
                     # никак не связано с аккаунтом на ranobelib.me
  db/               # модели и доступ к БД приложения (пользователи, личная библиотека,
                     # активность, история загрузок) — отдельно от SDK cache_dir
  exceptions.py     # маппинг RanobeLibError → HTTP-статус/сообщение
  jobs/             # фоновые задачи для download_title() и массового экспорта
  templates/        # Jinja2-шаблоны экранов
  static/
tests/
```

Ключевой принцип: SDK вызывается только из `services/`. Роуты не создают `RanobeLib(...)`
напрямую и не ловят `RanobeLibError` — это делает единый middleware/exception handler
(раздел «Обработка ошибок» ниже), а не каждый обработчик по отдельности.

`db/` (БД приложения) и SDK `cache_dir` — разные вещи и не должны смешиваться: `cache_dir`
хранит публичный кэш сырых ответов ranobelib.me, общий для всех пользователей; `db/`
хранит приватные данные приложения (кто есть кто, у кого что в личной библиотеке, кто что
сегодня читал/скачивал). Не писать пользовательские данные в `cache_dir` и не пытаться
обойтись без БД, храня их поверх SDK-кэша.

## Обязательные решения из ТЗ (не переоткрывать по ходу разработки)

Эти решения уже приняты в ТЗ — не спрашивать их заново, реализовывать как есть:

- **Кэш** — один общий `cache_dir` на всё приложение (не per-user/per-session), т.к. данные
  публичные и общие для всех пользователей. `cache_dir` — на персистентном volume при
  деплое в контейнере, иначе кэш обнуляется на каждом рестарте. `cache_ttl` подобрать так,
  чтобы новая глава на проде была видна без ручного `refresh=True` в разумный срок (часы,
  не дни) — значение явно закладывается в конфиг, не хардкодится.
- **Долгие операции** (`download_title()`, экспорт многих глав) — background job + прогресс
  (polling или SSE), не синхронный HTTP-запрос, который висит до готовности. Индикатор
  «глава N из M» обязателен для `download_title()`. Для одной главы/тома — синхронная отдача
  приемлема, если не появится причина решить иначе.
- **Экспорт** — временный файл экспорта удаляется после отдачи ответа (либо отдаётся из
  памяти/потока). Не оставлять мусор в `/tmp` между запросами.
- **Форматы экспорта** — брать из `ranobelib.exporters.EXPORTERS` динамически, никогда не
  хардкодить список `["txt", "fb2", "epub", "pdf"]`. Если `"pdf"` отсутствует в словаре
  (нет WeasyPrint на сервере) — просто не показывать эту опцию в UI, не падать и не
  выводить ошибку.
- **Неоднозначные переводы** (`MultipleTranslationsError` / `MultipleTitleTranslationsError`)
  — сайт обязан явно предложить выбор пользователю, никогда не выбирать `branch_id`/
  `translation_index` сам по умолчанию (тот же принцип, что и в самом SDK).
- **Авторизация** — своя, уровня приложения: email/пароль, регистрация/логин/логаут,
  серверные сессии (см. `app/auth/`). Нужна для персональной библиотеки и активности
  (PR 13+). Никак не связана с аккаунтом на ranobelib.me и не пытается его эмулировать —
  это раскрывает старое решение «не реализовывать авторизацию», которое имело в виду именно
  логин на ranobelib.me через SDK. `AuthRequiredError` от SDK (недоступный на сайте контент)
  по-прежнему просто «недоступно» — это другая сущность, не наша авторизация.
- **Оставшееся время загрузки** («Загрузки», PR 17) — считается на web-слое, по таймингу
  между тиками `on_chapter(completed, total)` из `download_title()`. Отдельного issue в SDK
  для этого заводить не нужно: SDK уже отдаёт прогресс по главам, экстраполяция оставшегося
  времени — обычная логика веб-слоя, не про ранобэ.
- **Параллельные запросы к API в обход SDK** — запрещены. Не создавать несколько
  `RanobeLib`-инстансов на один тайтл ради ускорения, не добавлять свой семафор/пул поверх
  `ApiClient` — он уже рейт-лимитирует и пейсит запросы.

## Обработка ошибок

Один центральный маппинг `RanobeLibError` → HTTP-ответ (exception handler в FastAPI, не
try/except в каждом роуте):

| Исключение SDK | HTTP | Сообщение пользователю |
|---|---|---|
| `TitleNotFoundError` | 404 | «Тайтл не найден, проверьте ссылку» |
| `ChapterNotFoundError` | 404 | «Глава не найдена» |
| `VolumeNotFoundError` | 404 | «Том не найден» |
| `MultipleTranslationsError` | 300/409 + список вариантов | UI выбора перевода |
| `MultipleTitleTranslationsError` | 300/409 + список вариантов | UI выбора по каждой неоднозначной главе / общий branch_id на тайтл |
| `AuthRequiredError` | 403 | «Требуется авторизация — недоступно» |
| `RateLimitError` | 429 | «ranobelib сейчас ограничивает запросы, попробуйте позже» |

Технические детали исключения — в логи сервера, никогда в тело ответа пользователю.

## Roadmap

Внутри PR — атомарные коммиты**, по одному на логический шаг (перечислены под каждой
фичей) — не сваливать фичу в один коммит и не смешивать несколько фич в одном PR. Порядок
важен: PR 2–3 — инфраструктурные и нужны почти всем остальным; PR 7 (выбор перевода)

184. **Требования к паролю при регистрации и смене пароля** — диагностика: `register()`
     (`POST /register`, `app/api/auth.py`) и `update_password()` (`POST /settings/security`,
     `app/api/settings.py`) сейчас проверяют только совпадение пароля с подтверждением и то, что
     он укладывается в 72-байтный лимит bcrypt (`hash_password()`/`PasswordTooLongError`,
     `app/auth/passwords.py`) — минимальной длины или любых других требований нет вообще, пароль
     из одного символа проходит оба маршрута; `register.html`/`settings_security.html` тоже не
     задают полям пароля ни `minlength`, ни подсказки — только `required`. Решение — стандарт NIST
     SP 800-63B (Digital Identity Guidelines, раздел про memorized secrets), а не устаревшие
     «классы символов»: минимальная длина 8 символов (сам NIST требует минимум 8, рекомендует по
     возможности поощрять 12+ — можно отразить это подсказкой в UI, не жёстким требованием),
     максимум — уже существующий de facto лимит bcrypt в 72 байта (менять не нужно, только
     сообщать понятной формой ошибки, а не только через `PasswordTooLongError`); НЕ требовать
     обязательных классов символов (заглавная буква/цифра/спецсимвол) — NIST прямо не рекомендует
     такие правила: они не повышают стойкость, а подталкивают к предсказуемым паттернам вроде
     `Password1!`; вместо этого NIST рекомендует сверять пароль со списком скомпрометированных/
     самых частых значений (§5.1.1.2) — для этого пункта достаточно небольшого встроенного
     блок-листа самых очевидных значений (`password`, `12345678`, локальная часть email и т.п.),
     полноценная проверка через k-anonymity API (например Have I Been Pwned) — возможное отдельное
     расширение, не блокирует эту правку. Коммиты: `validate_password_strength()` в
     `app/auth/passwords.py` (минимум 8 символов + проверка по короткому встроенному блок-листу,
     новое исключение `PasswordTooWeakError` по аналогии с `PasswordTooLongError`) → подключение в
     `register()` тем же паттерном «ошибка → форма», что уже используется для
     `password != password_confirm` → подключение в `update_password()` (`app/api/settings.py`)
     тем же паттерном → `minlength="8"` и текстовая подсказка под полем нового пароля в
     `register.html` и `settings_security.html` → тест на однобуквенный/пустой/из блок-листа
     пароль при регистрации и при смене пароля (форма-ошибка, не 500), тест на границе (8 символов
     проходит, 7 — нет; 72 байта проходит, 73 — нет).

185. **Предупреждение о cookie** — диагностика: приложение уже пишет визитёру несколько cookie без
     единого уведомления об этом — `session` (подписанная сессионная cookie входа,
     `RememberMeSessionMiddleware`, `app/auth/session_middleware.py`, `httponly`+`samesite=lax`)
     для залогиненного визитёра, и — для абсолютно любого визитёра, залогинен он или нет —
     `recent_titles` (анонимная история просмотренных тайтлов, `app/recent_titles.py`, тоже
     `httponly`+`samesite=lax`, до 180 дней). Ни баннера, ни ссылки на пояснение про cookie нигде в
     `base.html` нет. Решение — не модальное согласие, блокирующее сайт (оба cookie строго
     функциональные/необходимые для работы самого сервиса — вход и история просмотров, а не
     трекинг/реклама, то есть по GDPR/ePrivacy формально не требуют предварительного opt-in, только
     информирование), а ненавязчивый баннер внизу экрана при первом визите: короткий текст («Сайт
     использует cookie для входа и истории просмотров»), одна кнопка «Понятно», после клика — не
     показывать больше этому визитёру. Состояние «баннер закрыт» хранить в `localStorage`
     (`cookieNoticeDismissed`), а не заводить под это ещё одну cookie — было бы странно добавлять
     cookie специально для того, чтобы запомнить согласие на cookie, а `localStorage` для этого не
     нужен на сервере, только на клиенте; `base.html` уже применяет ровно этот приём для
     `sidebarExpanded` (инлайн-скрипт в начале `<body>`, синхронно, до первой отрисовки, чтобы не
     мелькнуть баннером тому, кто уже согласился). Коммиты: `_cookie_notice.html` партиал (баннер:
     текст + кнопка «Понятно», по образцу `_locked_feature.html`) → инлайн-скрипт в `base.html` по
     образцу существующего скрипта для `sidebarExpanded`, скрывающий баннер, если
     `localStorage.getItem("cookieNoticeDismissed") === "1"` → `cookie-notice.js`
     (`app/static/js/`) — обработчик клика на «Понятно», пишет `localStorage` и скрывает баннер без
     перезагрузки → подключение партиала и скрипта в `base.html` (рендерится на каждой странице, как
     и весь остальной shell) → проверка: баннер показывается при первом визите (чистый
     `localStorage`), не показывается повторно после клика «Понятно» и не мелькает при последующих
     навигациях по сайту.

186. **Баг: клик по скачанному тайтлу в истории загрузок ведёт на страницу тайтла, а не на
     скачивание файла** — диагностика: `download_history_list()`
     (`app/templates/_download_history.html`) рендерит для каждой записи истории две разных
     ссылки — заголовок-ссылку `<a class="downloads-history__link"
     href="/titles/{{ entry.slug_url }}">{{ entry.slug_url }}</a>` (строка 5, ведёт безусловно на
     страницу тайтла независимо от `entry.status`) и отдельную маленькую кнопку «Скачать» (строки
     13–15), которая появляется, только если `entry.id in ready_files` — а `ready_files`
     (`show_downloads()`, `app/api/downloads_section.py`) заполняется через `ready_file_url()`
     (`app/jobs/store.py`) лишь пока экспортированный файл ещё физически лежит на диске (не был
     скачан и не истёк TTL, см. `sweep_expired_result_files()`). Именно основная ссылка-заголовок —
     самый заметный кликабельный элемент строки (то, что видно на скриншоте: клик по названию
     тайтла со статусом «Готово» уводит на `/titles/...`, а не отдаёт файл), а не маленькая кнопка
     «Скачать» рядом с ней. Решение — не убирать кнопку «Скачать» (она остаётся явным
     альтернативным способом), а сделать саму ссылку-заголовок контекстно-зависимой: пока файл ещё
     доступен (`entry.id in ready_files`) она должна вести на тот же URL скачивания файла, что и
     кнопка «Скачать» (`ready_files[entry.id]`, обычный `FileResponse` с
     `Content-Disposition: attachment` — переход по ссылке инициирует скачивание, а не навигацию), и
     только когда файл уже выдан/истёк по TTL — падать назад на `/titles/{{ entry.slug_url }}`
     (единственный оставшийся осмысленный переход в этом случае — начать скачивание заново со
     страницы тайтла). Коммиты: условный `href` на `downloads-history__link` в
     `_download_history.html` (`ready_files[entry.id]`, если запись есть в `ready_files`, иначе
     прежний `/titles/{{ entry.slug_url }}`) → проверка на записи с ещё живым файлом (переход =
     скачивание, как у кнопки «Скачать» рядом) → проверка на записи, где файл уже скачан/истёк
     (переход по-прежнему на страницу тайтла, поведение не регрессирует) → проверка на записи со
     статусом `error` (ссылка не должна пытаться скачать несуществующий файл — остаётся на страницу
     тайтла всегда, `ready_files` для такой записи и так пуст, т.к. `list_ready_jobs_for_user()`/
     `ready_file_url()` фильтруют по `status == "done"`).

187. **Secure-флаг сессионной cookie и обязательный `SESSION_SECRET_KEY` в проде** — диагностика:
     `RememberMeSessionMiddleware` (`app/auth/session_middleware.py`) поддерживает `https_only`
     (добавляет `; secure` к `Set-Cookie`, см. `self.security_flags`), но
     `app.add_middleware(RememberMeSessionMiddleware, ...)` в `app/main.py` этот параметр вообще не
     передаёт — значит он всегда остаётся `False` по умолчанию, и cookie `session` уходит без флага
     `Secure` даже если сайт задеплоен по HTTPS, что оставляет её уязвимой к перехвату при случайном
     даунгрейде на HTTP или при MITM на пути. Отдельно — `get_settings()` (`app/config.py`) при
     отсутствующей переменной окружения `SESSION_SECRET_KEY` молча генерирует случайный ключ на
     каждый рестарт процесса и только логирует предупреждение — этого достаточно для локальной
     разработки, но для реального деплоя означает, что забытая переменная окружения не мешает
     приложению запуститься с ключом, который разлогинивает всех при каждом рестарте/деплое, вместо
     понятной ошибки конфигурации на старте. Решение: флаг окружения (например
     `ENVIRONMENT=production`, читаемый в `Settings`) — при нём `https_only=True` передаётся в
     `RememberMeSessionMiddleware`, а отсутствие явного `SESSION_SECRET_KEY` — это `RuntimeError`
     при старте, а не предупреждение в лог; при разработке (флаг не установлен или
     `=development`) поведение остаётся как сейчас (без `secure`, со случайным ключом и
     предупреждением), чтобы не потребовать HTTPS/явный секрет для локального запуска. Коммиты:
     поле `environment`/`is_production` в `Settings` (`app/config.py`) → `RuntimeError` вместо
     `logger.warning()` при пустом `SESSION_SECRET_KEY` и `is_production` → `https_only=
     get_settings().is_production` при добавлении `RememberMeSessionMiddleware` в `app/main.py` →
     обновление README/деплой-инструкции (обязательные переменные окружения для прод-деплоя) →
     тест, что приложение падает на старте без `SESSION_SECRET_KEY` при `ENVIRONMENT=production`, но
     не при его отсутствии.

188. **Rate limiting на вход и регистрацию** — диагностика: `POST /login` (`app/api/auth.py`)
     никак не ограничивает число попыток — сообщение об ошибке уже одинаковое что для
     несуществующего email, что для неверного пароля (правильно, не даёт энумерировать почты), но
     ничего не мешает перебирать пароли для одного email (или проверять занятость email через
     `POST /register`) сколь угодно быстро — ни блокировки по IP/аккаунту, ни задержки, ни капчи.
     Для приложения без выхода в реальный трафик это было не критично, для деплоя — стандартный
     вектор credential stuffing/перебора. Решение — не полноценный WAF, а простое
     rate-limiting middleware/зависимость (например `slowapi`/`starlette-limiter` поверх in-memory
     хранилища, в духе уже принятого MVP-подхода к job store из `app/jobs/store.py`) на
     `POST /login` и `POST /register` — разумный лимит (например не больше N попыток в минуту на
     IP+email), 429 с понятным сообщением при превышении, не мешающий обычному сценарию (одна
     опечатка в пароле). Коммиты: выбор и подключение rate-limiting зависимости → лимит на
     `POST /login` (по IP и/или по email из формы) → тот же лимит на `POST /register` → понятное
     сообщение об ошибке (`login.html`/`register.html`, статус 429) → тест, что N+1-я попытка входа
     с неверным паролем за короткое окно возвращает 429, а не 400, и что успешный вход после
     нескольких неудачных попыток всё ещё возможен, пока лимит не исчерпан.

189. **Базовые security-заголовки HTTP-ответов** — диагностика: `app/main.py` не добавляет ни
     одного security-заголовка — ни `Content-Security-Policy`, ни `X-Content-Type-Options`, ни
     `Referrer-Policy`, ни `X-Frame-Options`/`frame-ancestors`, ни `Strict-Transport-Security` —
     только `RememberMeSessionMiddleware`. Само по себе это не конкретная уязвимость (markdown уже
     санитизируется через `nh3`, см. вводный абзац волны), но это стандартный слой defense-in-depth,
     отсутствие которого — типичная находка любого security-чеклиста перед реальным деплоем.
     Решение — небольшой middleware, проставляющий на каждый ответ: `X-Content-Type-Options:
     nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` (сайт
     никогда не встраивается во фрейм), базовый `Content-Security-Policy` под уже используемые
     источники (свои `static`/`avatars`/`comment-attachments`, инлайн-скрипты в `base.html` и
     других шаблонах — потребует либо вынести их в файлы, либо `nonce`/`unsafe-inline` как
     переходный вариант с явной пометкой техдолга), и `Strict-Transport-Security` только когда
     `is_production` (PR 187) — HSTS на голом HTTP-деве необратимо ломает локальный
     `http://localhost`. Коммиты: middleware `security_headers` в `app/main.py` (или отдельный
     модуль `app/security_headers.py`) с фиксированными заголовками (`nosniff`/`Referrer-Policy`/
     `X-Frame-Options`) → черновой `Content-Security-Policy` под текущий набор источников
     (static/avatars/comment-attachments + инлайн-скрипты, отметить как техдолг там, где пришлось
     разрешить `unsafe-inline`) → условный `Strict-Transport-Security`, только при `is_production`
     (зависит от PR 187) → тест, что ответ на любой роут несёт все фиксированные заголовки; ручная
     проверка в браузере, что ни одна существующая страница не сломалась под новым CSP (инлайн-
     скрипты `sidebar-toggle`/`download-ready` и т.д.).

190. **Скоупить статус/файл фоновой загрузки по владельцу, не полагаться только на
     непредсказуемость `job_id`** — диагностика: `GET /titles/{slug_url}/download/{job_id}`,
     `.../status` и `.../file` (`app/api/downloads.py`) вообще не требуют авторизации
     (`_get_job_or_404()` проверяет только совпадение `slug_url`, не `job.user_id`) — единственная
     защита чужого прогресса/файла скачивания от постороннего — непредсказуемость самого `job_id`
     (`uuid4()`, `app/jobs/store.py`). Это осознанное решение изначального дизайна (скачивание не
     требовало аккаунта, `create_job(..., user_id=None)` для анонимного визитёра, см.
     `app/jobs/store.py`) само по себе не уязвимость (контент публичный, не персональные данные), но
     для залогиненного визитёра это расходится с остальными write/read-эндпоинтами приложения,
     которые последовательно скоупят доступ по `user_id` (см. вводный абзац волны) — держать это
     расхождение осознанным, а не забытым, стоит явной защитой в глубину: если у задачи есть
     `user_id`, показывать/отдавать её только этому пользователю (403, не 404, чтобы не путать с
     «слот не найден» для действительно анонимных задач); задачи без `user_id` (анонимное
     скачивание) продолжают работать как сейчас, без проверки. Коммиты: `_get_job_or_404()`
     (`app/api/downloads.py`) принимает опционального `current_user` и при `job.user_id is not None
     and job.user_id != current_user.id` (включая `current_user is None`) кидает 403 → подключение
     `Depends(get_current_user)` на все три роута (`show_download_status`/`download_status`/
     `download_result_file`) → тест: чужой залогиненный визитёр получает 403 на статус/файл чужой
     задачи, аноним получает 403 на задачу залогиненного визитёра, задача без `user_id` (анонимное
     скачивание) доступна всем как раньше, владелец по-прежнему видит свою задачу.


## Что явно не делать

- Авторизацию/логин на ranobelib.me — наша своя авторизация (PR 13) уровня приложения к
  этому не имеет отношения и никак не интегрируется с аккаунтом на ranobelib.me.
- Запись/загрузку контента на ranobelib.me (SDK и API read-only).
- Парсить каталог RanobeLib в обход SDK — ни постоянно, ни как временный воркэраунд. Раздел
  «Все тайтлы» (PR 15) реализуется только после появления метода листинга каталога в самом
  SDK; до тех пор PR остаётся заблокированным, а не обходится самодельным скрапингом.
- Иллюстрации в fb2/txt-экспорте — ограничение самого SDK, не создавать в UI впечатление,
  что это возможно для этих двух форматов (не показывать превью картинок как будто они
  попадут в fb2/txt).
- Свой кэш метаданных/глав поверх SDK-кэша (это отдельно от БД приложения из PR 13 —
  personal-library/активность/пользователи не кэш SDK-данных, а собственные данные
  приложения, см. раздел «Архитектура»).
- Хардкод списка форматов экспорта.
- Парсинг русского названия тайтла или расчёт объёма/веса новеллы на веб-слое без
  предварительной проверки, что этого нет в актуальной версии SDK (см. PR 25, PR 29 и
  Golden rule выше) — сначала проверка SDK/issue, потом, если необходимо, воркэраунд.
- Хардкод списка жанров (id → название) на веб-слое ради чекбоксов фильтра в каталоге
  (см. PR 38) — в SDK `0.6.1` нет публичного метода листинга жанров, значит сначала issue
  в репозитории SDK, PR остаётся заблокированным до его релиза, а не обходится своим
  захардкоженным списком.
- Хардкод списка стран на веб-слое ради раздела «Страна» в панели «Фильтры» (см. PR 85) —
  тот же принцип, что и с жанрами: в SDK `0.7.0` нет ни поля страны, ни метода её листинга,
  значит сначала issue в репозитории SDK, раздел остаётся заблокированным до его релиза.
- Фильтрация по тегам или по автору/художнику/переводческой команде (см. PR 86, PR 87)
  через выкачивание всего каталога и ручную фильтрацию на веб-слое в обход отсутствующего
  параметра в `Catalog.list_titles()` — сначала issue в репозитории SDK на нужный параметр,
  а не самодельный обход через массовую загрузку и локальную фильтрацию результатов.
- Мультивыбор страны (см. PR 100) через несколько последовательных вызовов
  `Catalog.list_titles(country=...)` (по одному на отмеченную страну) с объединением
  результатов на веб-слое — `country` в SDK `0.8.0` принимает только один id; сначала issue
  в репозитории SDK на список стран, PR остаётся заблокированным до его релиза, а не
  обходится N запросами и ручной склейкой страниц/пагинации.

## Git workflow

Один пункт roadmap выше = один PR. Один PR = набор атомарных коммитов (см. разбивку под
каждым пунктом roadmap), а не один гигантский коммит на всю фичу. Не смешивать в одном PR
изменения из разных пунктов roadmap, даже если технически проще. Сообщения коммитов —
consistently на одном языке (английский или русский) на весь репозиторий.

## Тесты

Мокать SDK на границе `services/` (не бить в реальный ranobelib.me в тестах). Отдельно
покрыть маппинг исключений — самая критичная для UX часть логики, легко сломать молча.
