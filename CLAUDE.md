# CLAUDE.md

Это новый репозиторий веб-приложения для чтения и скачивания ранобэ поверх
`ranobelib-python-sdk`. Полное ТЗ — в `TASK.md` в корне репозитория (перенеси туда
исходный документ, если его там ещё нет). Этот файл — оперативные инструкции для работы
в кодовой базе; при противоречии с ТЗ приоритет у ТЗ, а несоответствия — повод остановиться
и спросить, а не додумать самому.

## Что это за проект

Тонкий веб-слой поверх стабильного SDK (`ranobelib` на PyPI, `ranobelib-python-sdk>=0.3.0`).
Вся логика похода в API ranobelib.me, ретраи, рейт-лимитинг, кэш сырых ответов, парсинг
контента и генерация epub/fb2/txt/pdf — уже в SDK. Задача этого репозитория — UI и HTTP-слой
вокруг него, ничего из вышеперечисленного не дублировать и не переизобретать.

Golden rule: если чувствуешь, что пишешь код, который обходит SDK, добавляет параллельный
кэш тех же данных или сам сортирует/парсит номера глав — остановись, это, скорее всего,
уже сделано в SDK и его нужно просто вызвать.

### SDK — живая зависимость, не заморозка на 0.3.0

`ranobelib-python-sdk` активно разрабатывается, в нём могут появляться новые методы/поля/
возможности после `0.3.0`. Из этого следуют два обязательных правила, оба — до, а не после
того, как начал писать код:

1. **Перед тем как реализовывать что-либо своими руками на уровне сайта** (парсинг, доп.
   поле метаданных, недостающий фильтр, любую логику, которая выглядит как «логика про
   ранобэ», а не «логика веб-слоя») — сначала проверить PyPI, нет ли уже нужного в более
   свежей версии SDK, чем та, что закреплена в `pyproject.toml` (`pip index versions
   ranobelib-python-sdk`, страница пакета на pypi.org, `CHANGELOG.md` SDK). Не изобретать
   решение самостоятельно, не проверив это в первую очередь.
2. **Если нужной возможности нет даже в последней версии SDK** — завести issue в репозитории
   SDK: https://github.com/LLIJIYAPNIK/ranobelib-python-sdk/issues — что нужно и зачем,
   желательно с предлагаемой сигнатурой метода/примером использования, как остальной
   публичный API SDK. Не молча реализовывать эту логику внутри сайта в обход SDK. Сначала
   issue, потом — при необходимости — временный воркэраунд на сайте, явно помеченный как
   временный до появления фичи в SDK (например TODO-комментарием со ссылкой на issue).

Это тот же Golden rule, только сдвинутый по времени: не только «не дублируй то, что уже
есть в SDK», но и «не дублируй то, что скоро может появиться в SDK, вместо того чтобы это
туда предложить». Вся предметная логика про ранобэ (парсинг контента, номера глав,
экспорт, работа с API ranobelib.me) должна жить в SDK — этот репозиторий как был, так и
остаётся тонкой обёрткой вокруг него, а не местом, куда постепенно перетекает бизнес-логика.

## Стек и инструменты

- **Backend**: FastAPI (async, естественно сочетается с httpx/pydantic v2 стеком SDK).
  Не оборачивать вызовы SDK в `asyncio.run()` или thread-пулы — весь путь запроса должен
  быть async.
- **Пакетный менеджер**: `uv`. Зависимости — `uv add`, запуск — `uv run`.
- **Зависимость на SDK**: обычная PyPI-зависимость, `ranobelib-python-sdk>=0.3.0`. Никогда
  не переключать на path/git-зависимость на локальную копию SDK-репозитория, даже временно
  для отладки — если кажется, что в SDK баг, завести это отдельно, а не патчить его исходники
  внутри этого репозитория.
- **Фоновые задачи**: для MVP — in-memory job-очередь (однопроцессный деплой). Если понадобится
  горизонтальное масштабирование — Redis/RQ/Celery, но не вводить эту зависимость заранее
  без явной необходимости.
- **Frontend**: сервер-рендеринг (Jinja2) + минимум JS для интерактивности (выбор глав
  чекбоксами, поллинг/SSE прогресса долгих операций). Тяжёлый SPA-фреймворк не нужен, если
  не появится веская причина. Визуальная реализация экранов — не изобретать вёрстку заново,
  импортировать из Claude Design (см. раздел «Дизайн» ниже); `DESIGN_PROMPT.md` в корне
  репозитория — исходный промпт, из которого получены три концепции, оставлен для истории/
  контекста, актуальный источник вёрстки — сам файл концепции в Claude Design.
- **Данные приложения (пользователи, личная библиотека, активность, история загрузок)**:
  отдельная БД приложения (SQLite для MVP, `app/db/`) — не путать с SDK `cache_dir`, который
  остаётся публичным общим кэшем сырых ответов ranobelib.me. Хэш паролей — passlib/bcrypt,
  серверные сессии — стандартный session cookie (например `itsdangerous`/Starlette
  `SessionMiddleware`), без сторонних OAuth-провайдеров и без какой-либо интеграции с
  аккаунтом на ranobelib.me.

## Архитектура

```
app/
  api/            # HTTP-роуты (тонкие, без бизнес-логики)
  services/        # обёртка над RanobeLib: единственное место, где вызывается SDK
  auth/             # регистрация/логин/логаут, хэш паролей, сессии — уровень приложения,
                     # никак не связано с аккаунтом на ranobelib.me
  db/               # модели и доступ к БД приложения (пользователи, личная библиотека,
                     # активность, история загрузок) — отдельно от SDK cache_dir
  exceptions.py     # маппинг RanobeLibError → HTTP-статус/сообщение
  jobs/             # фоновые задачи для download_title() и массового экспорта
  templates/        # Jinja2-шаблоны экранов
  static/
tests/
```

Ключевой принцип: SDK вызывается только из `services/`. Роуты не создают `RanobeLib(...)`
напрямую и не ловят `RanobeLibError` — это делает единый middleware/exception handler
(раздел «Обработка ошибок» ниже), а не каждый обработчик по отдельности.

`db/` (БД приложения) и SDK `cache_dir` — разные вещи и не должны смешиваться: `cache_dir`
хранит публичный кэш сырых ответов ranobelib.me, общий для всех пользователей; `db/`
хранит приватные данные приложения (кто есть кто, у кого что в личной библиотеке, кто что
сегодня читал/скачивал). Не писать пользовательские данные в `cache_dir` и не пытаться
обойтись без БД, храня их поверх SDK-кэша.

## Обязательные решения из ТЗ (не переоткрывать по ходу разработки)

Эти решения уже приняты в ТЗ — не спрашивать их заново, реализовывать как есть:

- **Кэш** — один общий `cache_dir` на всё приложение (не per-user/per-session), т.к. данные
  публичные и общие для всех пользователей. `cache_dir` — на персистентном volume при
  деплое в контейнере, иначе кэш обнуляется на каждом рестарте. `cache_ttl` подобрать так,
  чтобы новая глава на проде была видна без ручного `refresh=True` в разумный срок (часы,
  не дни) — значение явно закладывается в конфиг, не хардкодится.
- **Долгие операции** (`download_title()`, экспорт многих глав) — background job + прогресс
  (polling или SSE), не синхронный HTTP-запрос, который висит до готовности. Индикатор
  «глава N из M» обязателен для `download_title()`. Для одной главы/тома — синхронная отдача
  приемлема, если не появится причина решить иначе.
- **Экспорт** — временный файл экспорта удаляется после отдачи ответа (либо отдаётся из
  памяти/потока). Не оставлять мусор в `/tmp` между запросами.
- **Форматы экспорта** — брать из `ranobelib.exporters.EXPORTERS` динамически, никогда не
  хардкодить список `["txt", "fb2", "epub", "pdf"]`. Если `"pdf"` отсутствует в словаре
  (нет WeasyPrint на сервере) — просто не показывать эту опцию в UI, не падать и не
  выводить ошибку.
- **Неоднозначные переводы** (`MultipleTranslationsError` / `MultipleTitleTranslationsError`)
  — сайт обязан явно предложить выбор пользователю, никогда не выбирать `branch_id`/
  `translation_index` сам по умолчанию (тот же принцип, что и в самом SDK).
- **Авторизация** — своя, уровня приложения: email/пароль, регистрация/логин/логаут,
  серверные сессии (см. `app/auth/`). Нужна для персональной библиотеки и активности
  (PR 13+). Никак не связана с аккаунтом на ranobelib.me и не пытается его эмулировать —
  это раскрывает старое решение «не реализовывать авторизацию», которое имело в виду именно
  логин на ranobelib.me через SDK. `AuthRequiredError` от SDK (недоступный на сайте контент)
  по-прежнему просто «недоступно» — это другая сущность, не наша авторизация.
- **Оставшееся время загрузки** («Загрузки», PR 17) — считается на web-слое, по таймингу
  между тиками `on_chapter(completed, total)` из `download_title()`. Отдельного issue в SDK
  для этого заводить не нужно: SDK уже отдаёт прогресс по главам, экстраполяция оставшегося
  времени — обычная логика веб-слоя, не про ранобэ.
- **Параллельные запросы к API в обход SDK** — запрещены. Не создавать несколько
  `RanobeLib`-инстансов на один тайтл ради ускорения, не добавлять свой семафор/пул поверх
  `ApiClient` — он уже рейт-лимитирует и пейсит запросы.

## Обработка ошибок

Один центральный маппинг `RanobeLibError` → HTTP-ответ (exception handler в FastAPI, не
try/except в каждом роуте):

| Исключение SDK | HTTP | Сообщение пользователю |
|---|---|---|
| `TitleNotFoundError` | 404 | «Тайтл не найден, проверьте ссылку» |
| `ChapterNotFoundError` | 404 | «Глава не найдена» |
| `VolumeNotFoundError` | 404 | «Том не найден» |
| `MultipleTranslationsError` | 300/409 + список вариантов | UI выбора перевода |
| `MultipleTitleTranslationsError` | 300/409 + список вариантов | UI выбора по каждой неоднозначной главе / общий branch_id на тайтл |
| `AuthRequiredError` | 403 | «Требуется авторизация — недоступно» |
| `RateLimitError` | 429 | «ranobelib сейчас ограничивает запросы, попробуйте позже» |

Технические детали исключения — в логи сервера, никогда в тело ответа пользователю.

Внутри PR — атомарные коммиты**, по одному на логический шаг (перечислены под каждой

191. **Перевести приложение на Postgres** — не «ranobe-доменная логика», Golden Rule и
     проверка SDK неприменимы (см. явную оговорку в разделе «Архитектура» CLAUDE.md: `db/`
     — собственные данные приложения, никак не связанные со слоем SDK/`cache_dir`) — это
     чисто инфраструктурная замена СУБД для уже существующей БД приложения. Диагностика
     текущего состояния: `app/db/connection.py` — сырой `sqlite3` (стандартная библиотека,
     не SQLAlchemy/асинхронный драйвер), `get_connection()` держит по одному
     `sqlite3.Connection` на поток (PR 67) к файлу на диске (`Settings.db_path`); миграции
     — свой минимальный раннер (`app/db/migrate.py`, сознательно без Alembic — «a single
     users table doesn't warrant the extra dependency», см. его же докстринг) поверх 16
     файлов `app/db/migrations/*.sql`, применяемых через `conn.executescript()` — метод
     специфичен для `sqlite3`, у драйверов Postgres такого нет вообще, нужно либо разбивать
     файл на отдельные `execute()`, либо (в psycopg3, в отличие от psycopg2) выполнять
     несколько стейтментов одним `execute()`, если в строке нет плейсхолдеров. Синтаксис
     самих миграций тоже частично SQLite-специфичен: `INTEGER PRIMARY KEY` (0001_users.sql
     и другие) — под Postgres нужно `GENERATED ALWAYS AS IDENTITY` (современный синтаксис,
     не устаревший `SERIAL`), тогда как `TEXT`/обычные `INTEGER`-колонки (даты хранятся как
     ISO-строки, булевы — как 0/1) переносятся как есть без переписывания под нативные
     `TIMESTAMP`/`BOOLEAN` — минимальная, а не «заодно идиоматичная» миграция. Плейсхолдеры
     `?` по всему `app/db/*.py` (`users.py`, `comments.py`, `library.py`, `downloads.py`,
     `activity.py`, `reactions.py`, `comment_reactions.py`, `notifications.py`) нужно
     заменить на `%s`; `sqlite3.Row` (доступ по имени колонки) — на `psycopg.rows.dict_row`
     (тот же паттерн доступа, другой класс). `cursor.lastrowid` (`users.py`/`comments.py`,
     после `INSERT`) — атрибут, специфичный для `sqlite3`, у psycopg его нет — переписать
     через `RETURNING id` в самом `INSERT` + `fetchone()`. `INSERT OR IGNORE`
     (`library.py`'s `add_entry()`) — SQLite-диалект, эквивалент в Postgres — `INSERT ...
     ON CONFLICT DO NOTHING`. Отдельно стоит отметить то, что переписывать НЕ нужно:
     `comment_reactions.py`/`reactions.py` уже используют `ON CONFLICT(...) DO UPDATE SET
     ... = excluded....` — этот синтаксис SQLite позаимствовал у Postgres дословно, работает
     без изменений на обеих СУБД. Решение по драйверу: `psycopg` (psycopg3) в его синхронном
     режиме — не переводить весь `app/db/` на async/await заодно с переездом на другую
     СУБД (два больших рискованных изменения одним PR); FastAPI и так прогоняет синхронные
     зависимости через пул потоков (`run_in_threadpool`, то же обоснование, что и у PR 67),
     так что per-thread-соединение из PR 67 сохраняется как паттерн, просто вместо голого
     соединения к файлу — соединение из пула `psycopg_pool.ConnectionPool` (соединение к
     Postgres — сетевой ресурс, а не файловый дескриптор, пул нужен уже не для «на всякий
     случай», а по существу). `Settings.db_path` (`app/config.py`) заменяется на
     `DATABASE_URL` (стандартная переменная окружения для строки подключения к Postgres,
     тот же формат, что ожидают большинство хостингов/docker-compose из PR 192). Тестовая
     обвязка (`tests/*.py`, сейчас сбрасывающая `_connection` между тестами на временный
     файл SQLite) тоже переходит на реальный Postgres — не держать два диалекта СУБД
     (SQLite для тестов, Postgres в проде) параллельно, это именно тот источник несовпадений
     между тестами и продакшном, которого лучше избегать; `ci.yml` получает `services:
     postgres` (нативная поддержка сервис-контейнеров в GitHub Actions) для прогона тестов.
     Коммиты: выбор драйвера и обоснование (psycopg3, синхронный режим — см. решение выше)
     → рефакторинг `app/db/migrate.py` под Postgres (разбиение/выполнение SQL-файлов без
     `executescript()`) → переписывание всех 16 файлов `app/db/migrations/*.sql`
     (`INTEGER PRIMARY KEY` → `GENERATED ALWAYS AS IDENTITY`, остальной синтаксис — по
     месту) → `app/db/connection.py` на `psycopg_pool.ConnectionPool` + `DATABASE_URL` →
     `app/config.py`: `db_path` → `DATABASE_URL` → по каждому файлу `app/db/*.py`:
     плейсхолдеры `?` → `%s`, `sqlite3.Row` → `dict_row`, `cursor.lastrowid` → `RETURNING
     id`, `INSERT OR IGNORE` → `ON CONFLICT DO NOTHING` → `ci.yml`: сервис-контейнер
     Postgres для тестов → тестовая обвязка на реальный Postgres вместо временного файла
     SQLite → полный прогон тестов, отдельная ручная проверка на реально поднятом Postgres
     (не только CI) — миграции применяются с нуля на пустой базе без ошибок.

     отправителя в уведомлениях (`_notification_card.html`'s `n.actor_name`). Два разных
     пользователя с одинаковым никнеймом сейчас неотличимы друг от друга в этих местах —
     не техническая путаница роутинга (PR 90 был прав, что по никнейму ничего не резолвится),
     а вопрос идентичности напоказ: ничто не мешает зарегистрировать второй аккаунт с
     никнеймом уже существующего пользователя и выдавать его комментарии/реакции за чужие
     (impersonation) — риска, которого не было до появления публичной социальной
     поверхности в волнах 13–14. Никнейм можно задать в двух местах — при регистрации
     (`POST /register`, `nickname: str = Form(default="")`, `app/api/auth.py`) и позже в
     настройках аккаунта (`update_user_profile()`, `app/db/users.py`, вызывается из
     `POST /settings/account`) — проверка на уникальность нужна в обоих, не только при
     регистрации. Никнейм необязателен (`nickname: str | None`) — проверка на уникальность
     применяется только когда он вообще указан (пустой/`None` не участвует в проверке,
     несколько пользователей без никнейма — не конфликт). Регистронезависимое сравнение
     (`Nick`/`nick`/`NICK` — тоже разные подписи визуально неотличимы для большинства
     скриптов, тот же принцип, что уже применяется к email через `_normalize_email()`),
     конкретный механизм — либо `UNIQUE`-индекс по `LOWER(nickname)` на уровне БД (после
     PR 191 — партиальный уникальный индекс в Postgres, `WHERE nickname IS NOT NULL`, чтобы
     не конфликтовать сам с собой на `NULL`-значениях — в отличие от `UNIQUE`-колонки,
     несколько `NULL` в Postgres/SQLite уникальности не нарушают, но лучше сделать это явно
     через `WHERE`, а не полагаться на это неявное поведение), либо проверка на уровне
     приложения (`SELECT` перед `INSERT`/`UPDATE`) — как и у email, нужна защита от гонки
     двух одновременных регистраций с одинаковым никнеймом, то есть проверка на уровне
     приложения одна не защищает полностью, БД-ограничение нужно в любом случае как
     backstop (та же логика, что уже применена к email — `UNIQUE` на колонке плюс
     дружелюбное сообщение об ошибке поверх него, не полагаться на проверку в Python как
     единственную защиту). Коммиты: миграция — уникальный индекс по `LOWER(nickname)` (с
     `WHERE nickname IS NOT NULL`) на таблице `users` → обработка нарушения этого
     ограничения в `POST /register` (дружелюбная ошибка формы «Этот никнейм уже занят», тот
     же паттерн, что и для занятого email) → та же проверка в `POST /settings/account`
     (`update_user_profile()`) → тест на гонку (две параллельные регистрации с одинаковым
     никнеймом — ровно одна должна пройти) → тест на регистронезависимость (`Nick` и `nick`
     — конфликт) → тест, что несколько пользователей без никнейма по-прежнему регистрируются
     без ошибок.

Пункты 195–196 — двадцать третья волна: последний шаг перед реальным запуском — открыть
приложение наружу под доменом (webnovells.ru) через nginx с TLS вместо голого `docker-compose`

195. **nginx + TLS для домена webnovells.ru** — диагностика: `docker-compose.yml` сейчас
     публикует приложение напрямую на хосте — `ports: ["8000:8000"]` — это биндится на все
     интерфейсы (`0.0.0.0:8000`), то есть уже сегодня сайт голым HTTP доступен снаружи по
     IP сервера на 8000-м порту, без TLS, без домена, без какой-либо защиты уровня прокси;
     `Dockerfile`'s `CMD` тоже не передаёт uvicorn `--proxy-headers`, поэтому `request.client.
     host` (`app/auth/auth.py`'s `_client_ip()`, ключ rate-limiter'а из PR 188) сейчас видит
     реальный IP посетителя напрямую. `db`-сервис в `docker-compose.yml`, для сравнения, уже
     правильно не публикует `ports:` вовсе — Postgres достаётся только `app` по внутренней
     docker-сети, наружу не торчит, тут ничего чинить не нужно. Решение — nginx на хосте (не
     ещё один сервис в `docker-compose.yml`: `app`/`db` резонно контейнеризовать — это
     основная логика приложения; nginx+certbot — стандартный, хорошо изученный путь именно
     как системный пакет, без лишней возни с volume под сертификаты и отдельным
     renewal-контейнером ради того же результата) как единственная точка входа на 80/443,
     проксирующая на `127.0.0.1:8000`, плюс TLS через Let's Encrypt (`certbot --nginx`,
     автопродление — системный таймер `certbot.timer`, который ставится вместе с пакетом
     на Debian/Ubuntu, отдельно настраивать не нужно). Конкретные пункты конфига, без которых
     часть уже существующей функциональности сайта будет не работать через прокси, а не
     просто «не защищена»: `client_max_body_size` — у nginx по умолчанию 1 МБ, а
     `MAX_VIDEO_SIZE_BYTES` в `app/comment_attachment.py` разрешает вложения к комментариям
     до 50 МБ — без явного увеличения лимита в конфиге nginx каждая такая загрузка будет
     падать с 413 ещё до того, как дойдёт до приложения; `proxy_read_timeout`/
     `proxy_send_timeout` — увеличить с дефолтных 60 с, синхронный экспорт одной главы/тома
     (см. `TASK.md`, «для отдельной главы/тома синхронная отдача приемлема») на медленном
     ответе ranobelib.me не должен обрываться прокси раньше, чем настоящим таймаутом
     приложения; `proxy_set_header X-Forwarded-For`/`X-Forwarded-Proto`/`Host` — и на стороне
     приложения `uvicorn --proxy-headers --forwarded-allow-ips=127.0.0.1` (или
     `ProxyHeadersMiddleware` в `app/main.py`), иначе `request.client.host` после переезда за
     nginx всегда будет показывать адрес самого nginx, а не визитёра — сам rate-limiter не
     сломается (ключ `app/auth/rate_limit.py` и так включает email, не только IP, коллизий
     между разными пользователями не будет), но приложение полностью потеряет реальный IP
     визитёра для чего угодно ещё (логи, будущие фичи, разбор злоупотреблений) — включать
     доверие к заголовкам сразу вместе с самим прокси, не задним числом. Редирект `http://` →
     `https://` на 80-м порту (кроме ACME-challenge пути для самого certbot). Отдельным
     шагом — раз nginx становится единственной официальной точкой входа — сузить
     `docker-compose.yml`'s `ports: ["8000:8000"]` до `"127.0.0.1:8000:8000"`, чтобы порт
     8000 не был одновременно доступен извне в обход nginx/TLS (сейчас, до этой правки, он
     доступен и так и так — nginx ничего не «закрывает» сам по себе, если старый путь
     не убрать явно), и минимальный `ufw` на самом сервере — разрешить только 22/tcp
     (SSH), 80/tcp, 443/tcp, остальное по умолчанию deny (без fail2ban/SSH-ключей — это
     сознательно отдельный, более широкий пункт харденинга VPS, не про nginx конкретно,
     отложен). Коммиты: `deploy/webnovells.ru.conf` — версионируемый в репозитории конфиг
     nginx (server-блок 80 → редирект на 443 + ACME-challenge location, server-блок 443 с
     `client_max_body_size`/`proxy_read_timeout`/`proxy_set_header`-ами выше,
     `proxy_pass http://127.0.0.1:8000`) → `uvicorn --proxy-headers --forwarded-allow-ips=
     127.0.0.1` в `Dockerfile`'s `CMD` → `docker-compose.yml`: `ports: ["127.0.0.1:8000:8000"]`
     вместо `"8000:8000"` → проверка на реальном сервере: `certbot --nginx -d webnovells.ru`
     выпускает сертификат и сам правит `deploy/webnovells.ru.conf`-копию в
     `/etc/nginx/sites-available/` под TLS → `ufw allow 22,80,443/tcp` + `ufw enable` →
     проверка со стороны: сайт открывается по `https://webnovells.ru`, `http://` редиректит
     на `https://`, прямой `http://<IP сервера>:8000` больше не отвечает совсем, загрузка
     видео-вложения к комментарию весом ~30–40 МБ проходит без 413, а не только маленькие
     файлы.

196. **`DEPLOY.md` — подробная инструкция по деплою** — диагностика: PR 193 (волна 22)
     планировал отдельный `DEPLOY.md`, но по факту инструкция осела в `README.md`'s разделе
     «Deploying» — там сейчас только таблица переменных окружения, без единого слова про
     то, что перед `docker compose up` вообще нужно на самом сервере, про домен/DNS, про
     nginx/TLS (этой волны на момент PR 193 ещё не существовало) и про сам процесс первого
     / повторного деплоя. Отдельно: `.github/workflows/` содержит только `ci.yml` (lint +
     pytest) — `cd.yml` из PR 193 фактически не заведён, то есть сегодня деплой в любом
     случае ручной, инструкция должна описывать реальность (SSH на сервер + `git pull` +
     `docker compose up -d --build`), а не CD-пайплайн, которого нет. Решение — завести
     `DEPLOY.md` в корне (README не трогать по содержанию, кроме короткой ссылки на
     `DEPLOY.md` вместо своего раздела «Deploying», который туда переезжает целиком) с
     разделами: что нужно на сервере заранее (Docker + Docker Compose plugin, nginx,
     certbot, `ufw`); DNS — A-запись `webnovells.ru` (и, если нужен `www.`, отдельная
     A-запись или редирект — явно решить и прописать, а не оставить на усмотрение при
     деплое) на IP сервера, до выпуска сертификата, иначе `certbot --nginx` не сможет
     подтвердить домен; первый деплой по шагам — клонировать репозиторий, `.env` из
     `.env.example` (полный список переменных — как сейчас в README, включая обязательный
     `ENVIRONMENT=production`/`SESSION_SECRET_KEY`), `docker compose up -d --build`,
     установка `deploy/webnovells.ru.conf` (PR 195) в `/etc/nginx/sites-available/` +
     `nginx -t` + `systemctl reload nginx`, выпуск сертификата, `ufw`; повторный деплой
     после изменений (`git pull` → `docker compose up -d --build` — миграции применяются
     сами при старте приложения, `app/main.py`'s `lifespan()` вызывает `run_migrations()`
     на каждый старт, ручного шага не требуется — явно об этом написать, чтобы не
     выдумывался лишний шаг) и что CD этого пока не делает, деплой ручной, до PR 193;
     явное упоминание, что бэкапы Postgres/файлов, SSH-харденинг, мониторинг и ротация
     логов — не сделаны в этой волне, обсуждались отдельно и отложены (чтобы `DEPLOY.md`
     не создавал ложное впечатление полноты). Коммиты: `DEPLOY.md` — предварительные
     требования к серверу → раздел DNS → пошаговый первый деплой (клонирование, `.env`,
     `docker compose up`, nginx/certbot/ufw из PR 195) → раздел «обновление/повторный
     деплой» (ручной процесс, миграции применяются автоматически) → раздел «что не входит
     в эту инструкцию» (бэкапы/SSH-харденинг/мониторинг — отложены) → замена раздела
     «Deploying» в `README.md` на одну ссылку на `DEPLOY.md` → проверка «с нуля»: человек
     без предварительного контекста о проекте проходит `DEPLOY.md` шаг за шагом на чистом
     VPS и получает рабочий `https://webnovells.ru`.

## Git workflow

Один пункт roadmap выше = один PR. Один PR = набор атомарных коммитов (см. разбивку под
каждым пунктом roadmap), а не один гигантский коммит на всю фичу. Не смешивать в одном PR
изменения из разных пунктов roadmap, даже если технически проще. Сообщения коммитов —
consistently на одном языке (английский или русский) на весь репозиторий.
