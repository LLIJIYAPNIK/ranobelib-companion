# CLAUDE.md

Это новый репозиторий веб-приложения для чтения и скачивания ранобэ поверх
`ranobelib-python-sdk`. Полное ТЗ — в `TASK.md` в корне репозитория (перенеси туда
исходный документ, если его там ещё нет). Этот файл — оперативные инструкции для работы
в кодовой базе; при противоречии с ТЗ приоритет у ТЗ, а несоответствия — повод остановиться
и спросить, а не додумать самому.

## Что это за проект

Тонкий веб-слой поверх стабильного SDK (`ranobelib` на PyPI, `ranobelib-python-sdk>=0.3.0`).
Вся логика похода в API ranobelib.me, ретраи, рейт-лимитинг, кэш сырых ответов, парсинг
контента и генерация epub/fb2/txt/pdf — уже в SDK. Задача этого репозитория — UI и HTTP-слой
вокруг него, ничего из вышеперечисленного не дублировать и не переизобретать.

Golden rule: если чувствуешь, что пишешь код, который обходит SDK, добавляет параллельный
кэш тех же данных или сам сортирует/парсит номера глав — остановись, это, скорее всего,
уже сделано в SDK и его нужно просто вызвать.

### SDK — живая зависимость, не заморозка на 0.3.0

`ranobelib-python-sdk` активно разрабатывается, в нём могут появляться новые методы/поля/
возможности после `0.3.0`. Из этого следуют два обязательных правила, оба — до, а не после
того, как начал писать код:

1. **Перед тем как реализовывать что-либо своими руками на уровне сайта** (парсинг, доп.
   поле метаданных, недостающий фильтр, любую логику, которая выглядит как «логика про
   ранобэ», а не «логика веб-слоя») — сначала проверить PyPI, нет ли уже нужного в более
   свежей версии SDK, чем та, что закреплена в `pyproject.toml` (`pip index versions
   ranobelib-python-sdk`, страница пакета на pypi.org, `CHANGELOG.md` SDK). Не изобретать
   решение самостоятельно, не проверив это в первую очередь.
2. **Если нужной возможности нет даже в последней версии SDK** — завести issue в репозитории
   SDK: https://github.com/LLIJIYAPNIK/ranobelib-python-sdk/issues — что нужно и зачем,
   желательно с предлагаемой сигнатурой метода/примером использования, как остальной
   публичный API SDK. Не молча реализовывать эту логику внутри сайта в обход SDK. Сначала
   issue, потом — при необходимости — временный воркэраунд на сайте, явно помеченный как
   временный до появления фичи в SDK (например TODO-комментарием со ссылкой на issue).

Это тот же Golden rule, только сдвинутый по времени: не только «не дублируй то, что уже
есть в SDK», но и «не дублируй то, что скоро может появиться в SDK, вместо того чтобы это
туда предложить». Вся предметная логика про ранобэ (парсинг контента, номера глав,
экспорт, работа с API ranobelib.me) должна жить в SDK — этот репозиторий как был, так и
остаётся тонкой обёрткой вокруг него, а не местом, куда постепенно перетекает бизнес-логика.

## Стек и инструменты

- **Backend**: FastAPI (async, естественно сочетается с httpx/pydantic v2 стеком SDK).
  Не оборачивать вызовы SDK в `asyncio.run()` или thread-пулы — весь путь запроса должен
  быть async.
- **Пакетный менеджер**: `uv`. Зависимости — `uv add`, запуск — `uv run`.
- **Зависимость на SDK**: обычная PyPI-зависимость, `ranobelib-python-sdk>=0.3.0`. Никогда
  не переключать на path/git-зависимость на локальную копию SDK-репозитория, даже временно
  для отладки — если кажется, что в SDK баг, завести это отдельно, а не патчить его исходники
  внутри этого репозитория.
- **Фоновые задачи**: для MVP — in-memory job-очередь (однопроцессный деплой). Если понадобится
  горизонтальное масштабирование — Redis/RQ/Celery, но не вводить эту зависимость заранее
  без явной необходимости.
- **Frontend**: сервер-рендеринг (Jinja2) + минимум JS для интерактивности (выбор глав
  чекбоксами, поллинг/SSE прогресса долгих операций). Тяжёлый SPA-фреймворк не нужен, если
  не появится веская причина. Визуальная реализация экранов — не изобретать вёрстку заново,
  импортировать из Claude Design (см. раздел «Дизайн» ниже); `DESIGN_PROMPT.md` в корне
  репозитория — исходный промпт, из которого получены три концепции, оставлен для истории/
  контекста, актуальный источник вёрстки — сам файл концепции в Claude Design.

  которые отдаёт `services/` (см. «Архитектура» ниже), поведение (чекбоксы выбора глав,
  прогресс-бар, модалки выбора перевода и т.д.) — на реальные вызовы API этого приложения,
  а не оставляется статичным.

## Архитектура

```
app/
  api/            # HTTP-роуты (тонкие, без бизнес-логики)
  services/        # обёртка над RanobeLib: единственное место, где вызывается SDK
  exceptions.py     # маппинг RanobeLibError → HTTP-статус/сообщение
  jobs/             # фоновые задачи для download_title() и массового экспорта
  templates/        # Jinja2-шаблоны экранов
  static/
tests/
```

Ключевой принцип: SDK вызывается только из `services/`. Роуты не создают `RanobeLib(...)`
напрямую и не ловят `RanobeLibError` — это делает единый middleware/exception handler
(раздел «Обработка ошибок» ниже), а не каждый обработчик по отдельности.

## Обязательные решения из ТЗ (не переоткрывать по ходу разработки)

Эти решения уже приняты в ТЗ — не спрашивать их заново, реализовывать как есть:

- **Кэш** — один общий `cache_dir` на всё приложение (не per-user/per-session), т.к. данные
  публичные и общие для всех пользователей. `cache_dir` — на персистентном volume при
  деплое в контейнере, иначе кэш обнуляется на каждом рестарте. `cache_ttl` подобрать так,
  чтобы новая глава на проде была видна без ручного `refresh=True` в разумный срок (часы,
  не дни) — значение явно закладывается в конфиг, не хардкодится.
- **Долгие операции** (`download_title()`, экспорт многих глав) — background job + прогресс
  (polling или SSE), не синхронный HTTP-запрос, который висит до готовности. Индикатор
  «глава N из M» обязателен для `download_title()`. Для одной главы/тома — синхронная отдача
  приемлема, если не появится причина решить иначе.
- **Экспорт** — временный файл экспорта удаляется после отдачи ответа (либо отдаётся из
  памяти/потока). Не оставлять мусор в `/tmp` между запросами.
- **Форматы экспорта** — брать из `ranobelib.exporters.EXPORTERS` динамически, никогда не
  хардкодить список `["txt", "fb2", "epub", "pdf"]`. Если `"pdf"` отсутствует в словаре
  (нет WeasyPrint на сервере) — просто не показывать эту опцию в UI, не падать и не
  выводить ошибку.
- **Неоднозначные переводы** (`MultipleTranslationsError` / `MultipleTitleTranslationsError`)
  — сайт обязан явно предложить выбор пользователю, никогда не выбирать `branch_id`/
  `translation_index` сам по умолчанию (тот же принцип, что и в самом SDK).
- **Авторизация** — не реализовывать, не проектировать UI логина. `AuthRequiredError` →
  сообщение «недоступно», и всё.
- **Параллельные запросы к API в обход SDK** — запрещены. Не создавать несколько
  `RanobeLib`-инстансов на один тайтл ради ускорения, не добавлять свой семафор/пул поверх
  `ApiClient` — он уже рейт-лимитирует и пейсит запросы.

## Обработка ошибок

Один центральный маппинг `RanobeLibError` → HTTP-ответ (exception handler в FastAPI, не
try/except в каждом роуте):

| Исключение SDK | HTTP | Сообщение пользователю |
|---|---|---|
| `TitleNotFoundError` | 404 | «Тайтл не найден, проверьте ссылку» |
| `ChapterNotFoundError` | 404 | «Глава не найдена» |
| `VolumeNotFoundError` | 404 | «Том не найден» |
| `MultipleTranslationsError` | 300/409 + список вариантов | UI выбора перевода |
| `MultipleTitleTranslationsError` | 300/409 + список вариантов | UI выбора по каждой неоднозначной главе / общий branch_id на тайтл |
| `AuthRequiredError` | 403 | «Требуется авторизация — недоступно» |
| `RateLimitError` | 429 | «ranobelib сейчас ограничивает запросы, попробуйте позже» |

Технические детали исключения — в логи сервера, никогда в тело ответа пользователю.

## Roadmap

Продукт внедряется фичами по порядку ниже. **Каждая фича из этого списка — отдельный PR.
Внутри PR — атомарные коммиты**, по одному на логический шаг (перечислены под каждой
фичей) — не сваливать фичу в один коммит и не смешивать несколько фич в одном PR. Порядок
важен: PR 2–3 — инфраструктурные и нужны почти всем остальным; PR 7 (выбор перевода)
технически нужен и чтению (PR 6), и экспорту (PR 8), и скачиванию тайтла (PR 10) — их можно
начать раньше, но смержить только после PR 7 или явно замокать выбор перевода временно.

1. **Каркас проекта** — `uv init`, зависимость `ranobelib-python-sdk>=0.3.0`, скелет
   FastAPI-приложения (`app/api`, `app/services`, `app/exceptions.py`, `app/jobs`,
   `app/templates`, `app/static`), health-check роут, базовый CI/lint. Коммиты: init
   проекта → зависимости → скелет FastAPI → health-check → CI.

2. **Слой обращения к SDK и конфиг кэша** — `services/` как единственное место, создающее
   `RanobeLib(...)`; конфиг `cache_dir`/`cache_ttl` из окружения; заметка/докс про
   персистентный volume при деплое. Коммиты: клиент-обёртка → конфиг кэша → smoke-тест на
   мок SDK.

3. **Обработка ошибок SDK** — маппинг из таблицы в `exceptions.py`, единый FastAPI
   exception handler. Коммиты: маппинг исключений → handler → тесты на каждое исключение
   из таблицы.

4. **Поиск/открытие тайтла** — форма ввода ссылки/`{id}--{slug}`, вызов `get_info()`,
   `TitleNotFoundError` идёт через готовый handler из PR 3. Коммиты: роут и форма →
   вызов SDK → обработка «не найден» → (опц.) заготовка под историю тайтлов.

5. **Страница тайтла и оглавление** — рендер метаданных, `get_table_of_contents()`
   (сортировка не трогается, приходит готовой), бейдж «N переводов», чекбоксы выбора глав
   (UI, без самого экспорта). Коммиты: метаданные тайтла → оглавление тома/главы → бейдж
   переводов → чекбоксы выбора (UI-заготовка под PR 8).

6. **Онлайн-чтение главы** — `get_chapter()`, рендер контента с явным решением по
   экранированию, навигация пред./след. глава, `ChapterNotFoundError`/`VolumeNotFoundError`.
   Коммиты: роут чтения → рендер контента и решение по санитизации → навигация между
   главами.

7. **Выбор перевода** — UI при `MultipleTranslationsError`, проброс `branch_id` дальше
   в чтение/экспорт/скачивание. Коммиты: обработка исключения → UI выбора → проброс
   `branch_id` в зависимые эндпоинты (чтение, экспорт, download_title).

8. **Экспорт одной главы и нескольких выбранных глав** — форматы динамически из
   `EXPORTERS`, отдача файла, удаление временного файла после ответа. Коммиты: список
   форматов из `EXPORTERS` → экспорт одной главы → экспорт нескольких выбранных одним
   файлом → очистка временных файлов.

9. **Скачивание тома/томов** — `get_volume()`/`get_volumes()` + экспорт целиком.
   Коммиты: эндпоинт → UI кнопки на странице тайтла.

10. **Скачивание всего тайтла с прогрессом** — background job (in-memory очередь), эндпоинт
    старта и эндпоинт статуса (polling/SSE), обработка `MultipleTitleTranslationsError`
    (выбор по каждой неоднозначной главе или общий `branch_id`/`translation_index` на
    тайтл), UI «глава N из M». Коммиты: job-очередь → эндпоинт старта → эндпоинт статуса →
    обработка `MultipleTitleTranslationsError` → UI прогресса.

11. **История недавно открытых тайтлов** (опционально, не MVP, если не закрыто в PR 4).

12. **Полировка error UX** — сквозная проверка всех путей на `RateLimitError`,
    `AuthRequiredError` и остальные сообщения из таблицы, финальная проверка, что нигде не
    протекает трейсбек в ответ пользователю.

## Что явно не делать

- Авторизацию/логин на ranobelib.me.
- Запись/загрузку контента на ranobelib.me (SDK и API read-only).
- Полнотекстовый поиск по каталогу lib.social — SDK работает с одним тайтлом по ссылке.
- Иллюстрации в fb2/txt-экспорте — ограничение самого SDK, не создавать в UI впечатление,
  что это возможно для этих двух форматов (не показывать превью картинок как будто они
  попадут в fb2/txt).
- Свой кэш метаданных/глав поверх SDK-кэша.
- Хардкод списка форматов экспорта.

## Git workflow

Один пункт roadmap выше = один PR. Один PR = набор атомарных коммитов (см. разбивку под
каждым пунктом roadmap), а не один гигантский коммит на всю фичу. Не смешивать в одном PR
изменения из разных пунктов roadmap, даже если технически проще. Сообщения коммитов —
consistently на одном языке (английский или русский) на весь репозиторий.

## Тесты

Мокать SDK на границе `services/` (не бить в реальный ranobelib.me в тестах). Отдельно
покрыть маппинг исключений — самая критичная для UX часть логики, легко сломать молча.
